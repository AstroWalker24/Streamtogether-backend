## 1. Philosophy & Goals

### Core Principles

The authentication schema is designed around four axes:

**Correctness before convenience.** Every invariant enforced in the service layer (`internal/auth/service`) has a corresponding database-level defense. The database is the last line of defense against data corruption — it does not trust the application.

**Read-heavy optimization.** Authentication is a read-dominant workload. Every HTTP request that passes through auth middleware reads a token claim and (on WebSocket establishment) validates a session. Logins, refreshes, and device lookups are the hot paths. Write operations (registration, password change, session revocation) are infrequent by comparison. The index strategy reflects this balance.

**No wide tables.** Each table holds exactly the attributes that belong to that entity. Frequently-changing columns (e.g., `last_active_at` on sessions) are separated in design thinking from immutable columns (e.g., `created_at`) so that updates do not touch cold data unnecessarily.

**Normalized but pragmatically denormalized where it matters.** The `refresh_tokens` table carries `user_id` and `device_id` alongside `session_id`. This is intentional denormalization: it enables a single-table revocation query (`WHERE user_id = $1`) without a join, which is critical for the high-urgency "revoke all tokens for user" operation triggered by password change and logout-all.

**Foreign key integrity is non-negotiable.** Every FK relationship is declared. The database enforces referential integrity; the application does not rely solely on its own logic to maintain consistency.

## 2. Naming Conventions

| Element | Convention | Example |
|---|---|---|
| Table names | Plural `snake_case` | `users`, `refresh_tokens` |
| Column names | Singular `snake_case` | `user_id`, `token_hash` |
| Primary key | Always `id` | `id UUID` |
| Foreign key columns | `{referenced_table_singular}_id` | `user_id`, `session_id`, `device_id` |
| Boolean flags | `is_` prefix or clear adjective | `revoked`, `trusted`, `email_verified` |
| Timestamp columns | `_at` suffix | `created_at`, `expires_at`, `revoked_at` |
| Enum types | Singular `snake_case` with `_type` or plain noun | `user_status`, `device_platform` |
| Primary key constraints | `pk_{table}` | `pk_users` |
| Unique constraints | `uq_{table}_{column(s)}` | `uq_users_email` |
| Foreign key constraints | `fk_{table}_{column}` | `fk_sessions_user_id` |
| Check constraints | `ck_{table}_{description}` | `ck_users_email_format` |
| Indexes | `idx_{table}_{column(s)}` | `idx_sessions_user_id` |
| Partial indexes | `idx_{table}_{column(s)}_{qualifier}` | `idx_sessions_user_id_active` |
| Triggers | `trg_{table}_{action}` | `trg_users_updated_at` |
| Trigger functions | `fn_{action}` | `fn_set_updated_at` |

## 3. Standard Column Conventions

Every table in the authentication schema carries a consistent set of lifecycle columns. Deviations are documented per-table.

### Immutable audit columns (all tables)

| Column | Type | Default | Meaning |
|---|---|---|---|
| `id` | `UUID` | `gen_random_uuid()` | System-assigned primary key. Generated by the application using `google/uuid`; the DB default is a fallback, never the primary path. |
| `created_at` | `TIMESTAMPTZ` | `NOW()` | Set once on `INSERT`. Never updated. |

### Mutable audit columns (entity tables only)

| Column | Type | Default | Meaning |
|---|---|---|---|
| `updated_at` | `TIMESTAMPTZ` | `NOW()` | Maintained by a `BEFORE UPDATE` trigger (see §10). Never set manually by the application. |

### Soft-delete column (select tables)

| Column | Type | Default | Meaning |
|---|---|---|---|
| `deleted_at` | `TIMESTAMPTZ NULL` | `NULL` | Non-null signals soft deletion. See §11 for policy. |

### Revocation columns (sessions, refresh_tokens, devices)

| Column | Type | Default | Meaning |
|---|---|---|---|
| `revoked` | `BOOLEAN` | `FALSE` | `TRUE` once explicitly terminated. Not the same as expiry. |
| `revoked_at` | `TIMESTAMPTZ NULL` | `NULL` | Set at the same time as `revoked = TRUE`. |

### Token lifecycle columns (token tables)

| Column | Type | Default | Meaning |
|---|---|---|---|
| `expires_at` | `TIMESTAMPTZ` | — | Hard expiry. Set at creation, never extended. |
| `used_at` | `TIMESTAMPTZ NULL` | `NULL` | Non-null signals the token has been consumed. |

## 4. PostgreSQL Types & Extensions

### Extensions required

| Extension | Purpose | When loaded |
|---|---|---|
| `pgcrypto` | `gen_random_uuid()` on PostgreSQL < 13 | Migration 000001 |

On PostgreSQL 13+, `gen_random_uuid()` is a built-in function and the extension is not required. The migration enables it defensively.

### Native types in use

| Type | Used for | Rationale |
|---|---|---|
| `UUID` | All primary and foreign keys | 128-bit identifiers; no collision risk; opaque to clients; safe for distributed generation. |
| `TEXT` | Variable-length strings (email, username, hash, name) | No storage penalty vs. `VARCHAR(n)` in PostgreSQL. Length validation belongs to the application layer, not the database. |
| `BOOLEAN` | Flags (`revoked`, `trusted`, `email_verified`) | Native boolean; no `TINYINT` workaround needed. |
| `TIMESTAMPTZ` | All timestamps | Stores UTC with timezone offset. Safe across DST changes and server relocations. Never use `TIMESTAMP WITHOUT TIME ZONE` in production. |
| `INET` | IP addresses (`ip_address`, `last_ip_address`) | PostgreSQL's native IP type validates format, supports both IPv4 and IPv6, enables subnet-based queries if ever needed. Avoids storing invalid strings. |

## 5. Enum Definitions

Custom PostgreSQL enum types are defined in a dedicated migration so they can be referenced by all subsequent table migrations.

### `user_status`

Represents the lifecycle state of a user account.

```sql
CREATE TYPE user_status AS ENUM (
    'pending_verification',
    'active',
    'suspended',
    'deleted'
);
```

**Why an enum instead of TEXT + CHECK constraint?**  
PostgreSQL enums are stored as 4-byte integers internally (highly compact), are self-documenting, and prevent invalid values without a runtime string comparison. Adding new states requires `ALTER TYPE ... ADD VALUE`, which is a fast metadata-only operation.

**Trade-off:** Enum values cannot be removed without recreating the type. Since auth account statuses are stable, this is acceptable.

### `device_platform`

Represents the client platform a device is associated with.

```sql
CREATE TYPE device_platform AS ENUM (
    'web',
    'ios',
    'android',
    'desktop'
);
```

**Why:** The same reasons as `user_status`. Platform values are a fixed vocabulary defined by the clients we support.

## 6. Table Designs

---

### 6.1 `users`

**Purpose:** The root identity record. Every authenticated entity on the platform traces back to a row in this table. It is the root aggregate for the authentication domain.

**Why this table exists:** Every session, device, token, and role assignment requires a stable user identity anchor. Without this table, nothing else in the authentication schema has meaning.

```sql
CREATE TABLE users (
    id               UUID          NOT NULL DEFAULT gen_random_uuid(),
    email            TEXT          NOT NULL,
    username         TEXT          NOT NULL,
    password_hash    TEXT          NOT NULL,
    status           user_status   NOT NULL DEFAULT 'pending_verification',
    email_verified   BOOLEAN       NOT NULL DEFAULT FALSE,
    created_at       TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    deleted_at       TIMESTAMPTZ   NULL,

    CONSTRAINT pk_users PRIMARY KEY (id),
    CONSTRAINT uq_users_email    UNIQUE (email),
    CONSTRAINT uq_users_username UNIQUE (username),
    CONSTRAINT ck_users_email_not_empty    CHECK (email    <> ''),
    CONSTRAINT ck_users_username_not_empty CHECK (username <> ''),
    CONSTRAINT ck_users_password_not_empty CHECK (password_hash <> ''),
    CONSTRAINT ck_users_deleted_at_status  CHECK (
        deleted_at IS NULL OR status = 'deleted'
    )
);
```

**Column notes**

| Column | Decision |
|---|---|
| `email` | Stored in lowercase canonical form. The application normalizes before `INSERT` and `SELECT`. The unique constraint is case-sensitive but the application always normalizes first — no need for a case-insensitive index on a plain column. A functional unique index on `lower(email)` (see §8) handles the edge case where legacy data may have mixed case. |
| `username` | Same normalization policy as email. |
| `password_hash` | The output of Argon2id. Never the plaintext. The `CHECK` constraint ensures an empty hash is never persisted — an empty hash would indicate a bug in the application, not a user choice. |
| `status` | Default is `pending_verification`. The transition to `active` happens when the email is verified. |
| `email_verified` | Redundant with `status` in one sense, but retained as a fast boolean read for middleware that needs to check verification without inspecting an enum value. |
| `deleted_at` | The `ck_users_deleted_at_status` constraint ensures that if `deleted_at` is set, `status` must be `'deleted'`. This prevents the two columns from diverging. |
| `updated_at` | Maintained by the `trg_users_updated_at` trigger (§10). |

**Soft delete:** Yes. `deleted_at` marks the start of the grace period. The identity columns (`email`, `username`) remain reserved until hard deletion. See §11.

### 6.2 `devices`

**Purpose:** Tracks the physical or logical endpoints from which a user has authenticated. Enables per-device session management and the device management interface.

**Why this table exists:** Without device tracking, session revocation is coarse — you can only revoke all sessions or none. Per-device records give users granular control and give the security model a per-device revocation surface.

**Why it comes before `sessions`:** Sessions reference devices, so devices must exist first.

```sql
CREATE TABLE devices (
    id                UUID            NOT NULL DEFAULT gen_random_uuid(),
    user_id           UUID            NOT NULL,
    fingerprint_hash  TEXT            NOT NULL,
    friendly_name     TEXT            NOT NULL DEFAULT '',
    platform          device_platform NOT NULL,
    browser           TEXT            NOT NULL DEFAULT '',
    os                TEXT            NOT NULL DEFAULT '',
    last_ip_address   INET            NOT NULL,
    first_seen_at     TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    last_active_at    TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    trusted           BOOLEAN         NOT NULL DEFAULT FALSE,
    revoked           BOOLEAN         NOT NULL DEFAULT FALSE,
    revoked_at        TIMESTAMPTZ     NULL,

    CONSTRAINT pk_devices              PRIMARY KEY (id),
    CONSTRAINT fk_devices_user_id      FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT ck_devices_revoked_at   CHECK (
        (revoked = FALSE AND revoked_at IS NULL) OR
        (revoked = TRUE  AND revoked_at IS NOT NULL)
    ),
    CONSTRAINT ck_devices_fingerprint_not_empty CHECK (fingerprint_hash <> '')
);
```

**Column notes**

| Column | Decision |
|---|---|
| `fingerprint_hash` | The SHA-256 hash of the derived device fingerprint. The raw signals (browser version, OS, client token) are never stored. The hash is used exclusively for device recognition lookups. |
| `friendly_name` | Empty string is the default — the application generates a name on first registration. Stored empty rather than nullable to simplify application code. |
| `platform` | Required for the device management UI. Stored as enum. |
| `browser`, `os` | Display-only text. No format constraint — values come from user-agent parsing which is inherently fuzzy. |
| `last_ip_address` | Updated on every login and token refresh. Only the most recent IP is retained in this table. Historical IP data, if needed for audit, belongs in an audit log table (not in scope here). |
| `first_seen_at` | Immutable after creation. Not controlled by the `updated_at` trigger — there is no `updated_at` on this table because the semantics of device updates are explicit (specific columns only). |
| `revoked` / `revoked_at` | The `ck_devices_revoked_at` constraint enforces consistency: you cannot have `revoked = TRUE` without `revoked_at`, and vice versa. |
| `trusted` | Reserved field. Always `FALSE` in the current implementation. |

**Cascade:** `ON DELETE CASCADE` from `users`. If a user is permanently deleted, all their device records are removed.

**No soft delete column (`deleted_at`):** Devices use `revoked` as their termination marker. A revoked device is not deleted — it is retained as an audit record. See §11.

### 6.3 `sessions`

**Purpose:** A stateful record of a user's authenticated context on a specific device within a specific time window. Sessions are the revocation anchor that makes it possible to invalidate access tokens indirectly.

**Why this table exists:** Access tokens (JWTs) are stateless and cannot be revoked individually. The session provides the server-side state that allows the system to refuse new refresh token issuances, effectively bounding the window during which a stolen access token remains useful.

```sql
CREATE TABLE sessions (
    id             UUID          NOT NULL DEFAULT gen_random_uuid(),
    user_id        UUID          NOT NULL,
    device_id      UUID          NOT NULL,
    ip_address     INET          NOT NULL,
    user_agent     TEXT          NOT NULL DEFAULT '',
    created_at     TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    last_active_at TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    expires_at     TIMESTAMPTZ   NOT NULL,
    revoked        BOOLEAN       NOT NULL DEFAULT FALSE,
    revoked_at     TIMESTAMPTZ   NULL,
    remember_me    BOOLEAN       NOT NULL DEFAULT FALSE,

    CONSTRAINT pk_sessions             PRIMARY KEY (id),
    CONSTRAINT fk_sessions_user_id     FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_sessions_device_id   FOREIGN KEY (device_id)
        REFERENCES devices (id) ON DELETE RESTRICT,
    CONSTRAINT ck_sessions_expires_future CHECK (expires_at > created_at),
    CONSTRAINT ck_sessions_revoked_at  CHECK (
        (revoked = FALSE AND revoked_at IS NULL) OR
        (revoked = TRUE  AND revoked_at IS NOT NULL)
    )
);
```

**Column notes**

| Column | Decision |
|---|---|
| `ip_address` | The IP address at session creation time. Not updated during the session lifetime — that would be a misleading record. The device's `last_ip_address` is updated instead. |
| `user_agent` | The raw user-agent string at session creation. Stored for display in the device management interface. Empty string default rather than NULL because the string is always present in HTTP requests. |
| `expires_at` | Set at creation, never modified. The `ck_sessions_expires_future` constraint ensures `expires_at > created_at`, preventing nonsensical records. |
| `last_active_at` | Updated on every successful token refresh. This is the write-hot column on this table. |
| `remember_me` | Controls the refresh token expiry duration at creation time. Not modified after creation. |

**Foreign key from `device_id`:** Uses `ON DELETE RESTRICT` rather than `CASCADE`. Devices should not be hard-deleted through normal application flows. If a device is purged (which would be an unusual administrative operation), the sessions table will refuse the deletion until sessions are handled explicitly. This prevents accidental orphaning.

**No `updated_at`:** Sessions have explicit `last_active_at` and `revoked_at` semantics. A generic `updated_at` would be misleading — callers care specifically whether the session was last refreshed or when it was revoked, not simply "when was this row last modified."

### 6.4 `refresh_tokens`

**Purpose:** Stores the server-side record of every refresh token issued. Used to validate, rotate, and detect replay of refresh tokens.

**Why this table exists:** Refresh tokens are opaque and long-lived. Without a server-side record, the server cannot validate, revoke, or detect replay of these credentials. The hash-only storage model ensures that a database breach does not leak usable token values.

```sql
CREATE TABLE refresh_tokens (
    id              UUID          NOT NULL DEFAULT gen_random_uuid(),
    session_id      UUID          NOT NULL,
    user_id         UUID          NOT NULL,
    device_id       UUID          NOT NULL,
    token_hash      TEXT          NOT NULL,
    issued_at       TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ   NOT NULL,
    consumed_at     TIMESTAMPTZ   NULL,
    revoked         BOOLEAN       NOT NULL DEFAULT FALSE,
    revoked_at      TIMESTAMPTZ   NULL,
    replaced_by_id  UUID          NULL,

    CONSTRAINT pk_refresh_tokens              PRIMARY KEY (id),
    CONSTRAINT uq_refresh_tokens_token_hash   UNIQUE (token_hash),
    CONSTRAINT fk_refresh_tokens_session_id   FOREIGN KEY (session_id)
        REFERENCES sessions (id) ON DELETE CASCADE,
    CONSTRAINT fk_refresh_tokens_user_id      FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_refresh_tokens_device_id    FOREIGN KEY (device_id)
        REFERENCES devices (id) ON DELETE RESTRICT,
    CONSTRAINT fk_refresh_tokens_replaced_by  FOREIGN KEY (replaced_by_id)
        REFERENCES refresh_tokens (id) ON DELETE SET NULL,
    CONSTRAINT ck_refresh_tokens_expires_future CHECK (expires_at > issued_at),
    CONSTRAINT ck_refresh_tokens_revoked_at CHECK (
        (revoked = FALSE AND revoked_at IS NULL) OR
        (revoked = TRUE  AND revoked_at IS NOT NULL)
    ),
    CONSTRAINT ck_refresh_tokens_hash_not_empty CHECK (token_hash <> '')
);
```

**Column notes**

| Column | Decision |
|---|---|
| `token_hash` | SHA-256 hex digest of the plaintext token. The unique constraint means no two tokens can ever produce the same hash — any collision would be a cryptographic failure, not a schema violation. |
| `user_id`, `device_id` | Denormalized from `sessions`. The cost of this denormalization (two extra UUID columns per row, ~16 bytes each) is justified by removing a join from two critical high-urgency operations: "revoke all tokens for user" (password change, logout-all) and "find all tokens for device" (device revocation). |
| `consumed_at` | Non-null signals the token has been used. This is checked first in the refresh flow. If a token is presented and `consumed_at IS NOT NULL`, it indicates a replay attack and the session must be revoked immediately. |
| `replaced_by_id` | Self-referencing FK forming the rotation chain. On `DELETE SET NULL`: if a successor token is purged (e.g., by a cleanup job that removes old tokens before its predecessor), the chain is broken gracefully rather than causing a cascading deletion. The audit trail is partial but the data is not corrupted. |

**No `created_at`:** `issued_at` serves this semantic purpose exactly. Adding `created_at` alongside would be redundant.

**No `updated_at`:** Refresh tokens are append-heavy, single-mutation entities. Once issued, only `consumed_at`, `revoked`, and `revoked_at` are ever written. A generic `updated_at` adds noise without value.

### 6.5 `roles`

**Purpose:** Named, stable collections of permissions. The primary unit of authorization assignment.

**Why this table exists:** Rather than assigning permissions directly to users (which would require updating every user when a permission set changes), permissions are grouped into roles. Changing the permissions of a role updates all users holding that role instantly.

```sql
CREATE TABLE roles (
    id          UUID        NOT NULL DEFAULT gen_random_uuid(),
    name        TEXT        NOT NULL,
    label       TEXT        NOT NULL DEFAULT '',
    description TEXT        NOT NULL DEFAULT '',
    is_system   BOOLEAN     NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_roles         PRIMARY KEY (id),
    CONSTRAINT uq_roles_name    UNIQUE (name),
    CONSTRAINT ck_roles_name_not_empty  CHECK (name <> '')
);
```

**Column notes**

| Column | Decision |
|---|---|
| `name` | Immutable system identifier (`user`, `moderator`, `admin`, `service`). The unique constraint is the database enforcement of the uniqueness invariant. The application never renames a role after creation. |
| `is_system` | `TRUE` for built-in roles seeded at deployment. The application layer checks this flag before allowing deletion. A future migration could add a `CHECK` constraint enforcing non-deletion of system roles, but the application-level check is sufficient for now. |
| `label`, `description` | Display-only. Not used in authorization logic. Default to empty string to avoid NULL handling in display code. |

**No `updated_at`:** Roles are seeded once and their `name` is immutable. The `label` and `description` may be updated, but there is no business requirement to track when a label last changed. If that becomes necessary, `updated_at` can be added in a future migration.

**No soft delete:** System roles must not be deleted. Custom roles (future) will be deleted by marking them `is_system = FALSE` and then hard-deleting. Soft deletion adds complexity without benefit for roles.

### 6.6 `permissions`

**Purpose:** Single, granular capabilities following the `resource:action` naming convention. The atomic units of the RBAC model.

**Why this table exists:** Permissions are defined at design time and seeded once. Storing them in the database makes them queryable, assignable to roles, and displayable in admin interfaces without code changes.

```sql
CREATE TABLE permissions (
    id          UUID        NOT NULL DEFAULT gen_random_uuid(),
    name        TEXT        NOT NULL,
    description TEXT        NOT NULL DEFAULT '',
    category    TEXT        NOT NULL DEFAULT '',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_permissions       PRIMARY KEY (id),
    CONSTRAINT uq_permissions_name  UNIQUE (name),
    CONSTRAINT ck_permissions_name_format CHECK (name ~ '^[a-z_]+:[a-z_]+$')
);
```

**Column notes**

| Column | Decision |
|---|---|
| `name` | Immutable. The `ck_permissions_name_format` constraint enforces the `resource:action` convention at the database level. A permission name that doesn't match this pattern is a programming error. |
| `category` | Grouping label for admin UI display (e.g., `party`, `chat`, `admin`). Not used in authorization logic. |

**Why `ck_permissions_name_format`?** The `resource:action` convention is a design invariant (from `authentication-domain-contracts.md`, §2.6). Encoding it as a CHECK constraint means the database will reject any seeding script or application code that violates it, catching bugs at the point of data insertion.

### 6.7 `user_roles`

**Purpose:** The many-to-many join between users and roles. The actual assignment of a capability bundle to a user.

```sql
CREATE TABLE user_roles (
    user_id     UUID        NOT NULL,
    role_id     UUID        NOT NULL,
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    assigned_by UUID        NULL,

    CONSTRAINT pk_user_roles          PRIMARY KEY (user_id, role_id),
    CONSTRAINT fk_user_roles_user_id  FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_user_roles_role_id  FOREIGN KEY (role_id)
        REFERENCES roles (id) ON DELETE RESTRICT,
    CONSTRAINT fk_user_roles_assigned_by FOREIGN KEY (assigned_by)
        REFERENCES users (id) ON DELETE SET NULL
);
```

**Column notes**

| Column | Decision |
|---|---|
| `assigned_at` | When the role was assigned. Useful for audit: "when did this user become an admin?" |
| `assigned_by` | The user who made the assignment. `NULL` for system-assigned roles (registration auto-assigns `user`). `ON DELETE SET NULL` ensures that deleting an admin account does not cascade to remove all the roles they ever assigned. |

**Primary key as composite:** `(user_id, role_id)`. No surrogate `id` needed — the combination is the identity. This also enforces uniqueness naturally.

**`ON DELETE RESTRICT` on `role_id`:** Prevents deletion of a role while users hold it. The application must unassign a role from all users before it can be deleted. This is intentional friction — deleting a role with active users is almost always a mistake.

**`ON DELETE CASCADE` on `user_id`:** If a user is permanently deleted, their role assignments are removed with them.

---

### 6.8 `role_permissions`

**Purpose:** The many-to-many join between roles and permissions. Defines the capability set of each role.

```sql
CREATE TABLE role_permissions (
    role_id       UUID        NOT NULL,
    permission_id UUID        NOT NULL,
    assigned_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_role_permissions              PRIMARY KEY (role_id, permission_id),
    CONSTRAINT fk_role_permissions_role_id      FOREIGN KEY (role_id)
        REFERENCES roles (id) ON DELETE CASCADE,
    CONSTRAINT fk_role_permissions_permission_id FOREIGN KEY (permission_id)
        REFERENCES permissions (id) ON DELETE RESTRICT
);
```

**Column notes**

| Column | Decision |
|---|---|
| `assigned_at` | When this permission was added to this role. Useful for auditing permission set evolution. |

**`ON DELETE CASCADE` on `role_id`:** If a role is deleted, its permission assignments are removed with it.

**`ON DELETE RESTRICT` on `permission_id`:** Prevents deletion of a permission while it is assigned to any role. Permissions are considered immutable (they are never renamed or removed — new ones are added as features grow). This constraint enforces that invariant at the database level.

### 6.9 `email_verification_tokens`

**Purpose:** Short-lived, single-use tokens delivered via email to confirm that the registered user controls their email address.

**Why this table exists:** The token must be validated server-side (the hash stored here is compared against the hash of the presented token), consumed on use, and invalidated when a new one is issued. These operations require a persistent record.

```sql
CREATE TABLE email_verification_tokens (
    id         UUID        NOT NULL DEFAULT gen_random_uuid(),
    user_id    UUID        NOT NULL,
    token_hash TEXT        NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    used_at    TIMESTAMPTZ NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_email_verification_tokens       PRIMARY KEY (id),
    CONSTRAINT uq_email_verification_token_hash   UNIQUE (token_hash),
    CONSTRAINT fk_email_verification_user_id      FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT ck_email_verification_expires CHECK (expires_at > created_at),
    CONSTRAINT ck_email_verification_hash_not_empty CHECK (token_hash <> '')
);
```

**Column notes**

| Column | Decision |
|---|---|
| `token_hash` | SHA-256 of the plaintext token. Unique constraint prevents hash collisions from being silently stored. |
| `used_at` | Null until the token is consumed. Non-null means the token is permanently invalid, regardless of `expires_at`. |

**Invariant enforcement note:** The single-active-token invariant (at most one valid token per user) is enforced by the application: before inserting a new token, the service calls `InvalidateAllForUser`, which sets `used_at = NOW()` on all existing unused tokens for that user. The database does not enforce this directly — a partial unique index cannot express "only one unconsumed token per user" cleanly in SQL. The service-layer contract is the enforcement point; the database ensures that each token hash is globally unique.

**`ON DELETE CASCADE` from `user_id`:** If a user is permanently deleted, their verification tokens are removed.

---

### 6.10 `password_reset_tokens`

**Purpose:** Short-lived, single-use tokens delivered via email that grant the right to set a new password.

```sql
CREATE TABLE password_reset_tokens (
    id         UUID        NOT NULL DEFAULT gen_random_uuid(),
    user_id    UUID        NOT NULL,
    token_hash TEXT        NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    used_at    TIMESTAMPTZ NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_password_reset_tokens      PRIMARY KEY (id),
    CONSTRAINT uq_password_reset_token_hash  UNIQUE (token_hash),
    CONSTRAINT fk_password_reset_user_id     FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT ck_password_reset_expires CHECK (expires_at > created_at),
    CONSTRAINT ck_password_reset_hash_not_empty CHECK (token_hash <> '')
);
```

**Column notes:** Identical pattern to `email_verification_tokens`. The same single-active-token invariant applies and is enforced the same way.

**Separation from `email_verification_tokens`:** These are distinct tables rather than a single generic `tokens` table. A single generic table would require a discriminator column and would complicate queries, constraints, and retention policies. The two token types have identical shapes but different semantics, different expiry windows (24h vs 1h), and potentially different retention requirements. Keeping them separate makes the intent explicit and each table simple.

```
users (root aggregate)
│
├── devices [1..n]
│   └─── fk: devices.user_id → users.id  (CASCADE on delete)
│
├── sessions [0..n]
│   ├─── fk: sessions.user_id   → users.id   (CASCADE on delete)
│   ├─── fk: sessions.device_id → devices.id (RESTRICT on delete)
│   │
│   └── refresh_tokens [0..n per session; ≤1 valid at any time]
│       ├─── fk: refresh_tokens.session_id    → sessions.id      (CASCADE on delete)
│       ├─── fk: refresh_tokens.user_id       → users.id         (CASCADE on delete)
│       ├─── fk: refresh_tokens.device_id     → devices.id       (RESTRICT on delete)
│       └─── fk: refresh_tokens.replaced_by_id → refresh_tokens.id (SET NULL on delete)
│
├── user_roles [0..n]
│   ├─── fk: user_roles.user_id     → users.id (CASCADE on delete)
│   └─── fk: user_roles.role_id     → roles.id  (RESTRICT on delete)
│
├── email_verification_tokens [0..1 valid at any time]
│   └─── fk: email_verification_tokens.user_id → users.id (CASCADE on delete)
│
└── password_reset_tokens [0..1 valid at any time]
    └─── fk: password_reset_tokens.user_id → users.id (CASCADE on delete)

roles [independently seeded]
│
└── role_permissions [0..n]
    ├─── fk: role_permissions.role_id       → roles.id       (CASCADE on delete)
    └─── fk: role_permissions.permission_id → permissions.id (RESTRICT on delete)

permissions [independently seeded]
```

### Relationship Type Reference

| Relationship | Type | Notes |
|---|---|---|
| `users` → `devices` | One-to-Many | A user owns zero-to-many devices. Each device belongs to exactly one user. |
| `users` → `sessions` | One-to-Many | A user has zero-to-many concurrent sessions. Each session belongs to one user. |
| `sessions` → `devices` | Many-to-One | Many sessions can reference the same device over time. Each session belongs to exactly one device. |
| `sessions` → `refresh_tokens` | One-to-Many | A session has zero-to-many token records (rotation chain), but at most one unconsumed token at any time. |
| `refresh_tokens` → `refresh_tokens` | Self-Referential | `replaced_by_id` forms the rotation chain. A consumed token points to its successor. |
| `users` → `roles` | Many-to-Many | via `user_roles`. A user holds one-to-many roles; a role is held by zero-to-many users. |
| `roles` → `permissions` | Many-to-Many | via `role_permissions`. A role grants zero-to-many permissions; a permission belongs to zero-to-many roles. |
| `users` → `email_verification_tokens` | One-to-Many | A user has at most one valid token at any time, but the history of previous tokens is retained. |
| `users` → `password_reset_tokens` | One-to-Many | Same policy as email verification. |

### Cascade Behavior Summary

| FK | On DELETE of parent | Reason |
|---|---|---|
| `sessions.user_id` | CASCADE | A user's sessions are meaningless without the user. |
| `sessions.device_id` | RESTRICT | Devices are not normally hard-deleted. Force explicit handling. |
| `refresh_tokens.session_id` | CASCADE | Tokens are meaningless without their session. |
| `refresh_tokens.user_id` | CASCADE | Tokens are meaningless without the user. |
| `refresh_tokens.device_id` | RESTRICT | Same as sessions → devices. |
| `refresh_tokens.replaced_by_id` | SET NULL | Partial audit chain is better than a cascaded deletion of predecessor tokens. |
| `devices.user_id` | CASCADE | Devices are meaningless without the user. |
| `user_roles.user_id` | CASCADE | Role assignments are meaningless without the user. |
| `user_roles.role_id` | RESTRICT | Prevent accidental role deletion while users hold it. |
| `user_roles.assigned_by` | SET NULL | Deleting an admin should not remove their assignment history. |
| `role_permissions.role_id` | CASCADE | Permission grants are meaningless without the role. |
| `role_permissions.permission_id` | RESTRICT | Prevent deletion of a permission still in use. |
| `email_verification_tokens.user_id` | CASCADE | Tokens are meaningless without the user. |
| `password_reset_tokens.user_id` | CASCADE | Tokens are meaningless without the user. |

## 8. Index Strategy

Indexes are the primary tool for making this schema fast. The auth domain has well-defined hot paths, which means the index design is deterministic rather than speculative.

### Hot paths (by frequency, descending)

1. **Token verification middleware** — Reads `AccessTokenClaims` from JWT; no DB hit. This is handled entirely in memory.
2. **Token refresh** — Lookup `refresh_tokens` by `token_hash`. Frequency: once per 15-minute access token expiry per active session.
3. **Session validation (WebSocket)** — Lookup `sessions` by `id`.
4. **Login** — Lookup `users` by `email` or `username`.
5. **Permission resolution** — Join `user_roles` → `role_permissions` → `permissions` by `user_id`. Heavily cached in Redis; DB hit is a cache miss.
6. **Session list** — List active `sessions` by `user_id` for the device management screen.
7. **Device list** — List active `devices` by `user_id`.
8. **Revocation writes** — Update `sessions` and `refresh_tokens` by `user_id` or `session_id`. Less frequent but latency-sensitive.

---

### 8.1 `users` Indexes

```sql
-- Login by email (most common login path)
CREATE UNIQUE INDEX uq_users_email_lower
    ON users (lower(email));

-- Login by username (second login path)
CREATE UNIQUE INDEX uq_users_username_lower
    ON users (lower(username));

-- Admin queries by account status
CREATE INDEX idx_users_status
    ON users (status);

-- Background cleanup: find soft-deleted users whose grace period has elapsed
CREATE INDEX idx_users_deleted_at
    ON users (deleted_at)
    WHERE deleted_at IS NOT NULL;
```

**Why functional unique indexes on `lower()`?** The `uq_users_email` and `uq_users_username` constraints on the table are case-sensitive. These functional indexes enforce case-insensitive uniqueness at the database level. Although the application normalizes to lowercase, defensive programming demands the database also enforce this — a bug in normalization logic should not be able to create `alice@example.com` and `ALICE@example.com` as two separate accounts.

**Why `idx_users_deleted_at` is partial?** The vast majority of users are not soft-deleted. A partial index (`WHERE deleted_at IS NOT NULL`) covers only the relevant fraction of the table, making it small and fast for the cleanup job that needs it.

---

### 8.2 `sessions` Indexes

```sql
-- Find session by ID (WebSocket authentication, token refresh path)
-- Covered by the PRIMARY KEY. No additional index needed.

-- List active sessions for device management UI
CREATE INDEX idx_sessions_user_id_active
    ON sessions (user_id, created_at DESC)
    WHERE revoked = FALSE;

-- Revoke all sessions for a device
CREATE INDEX idx_sessions_device_id
    ON sessions (device_id);

-- Background cleanup: find expired sessions
CREATE INDEX idx_sessions_expires_at
    ON sessions (expires_at)
    WHERE revoked = FALSE;
```

**Why `idx_sessions_user_id_active` is partial?** The device management UI only lists active sessions. A non-partial index would include all historical revoked sessions, making the index much larger and the scan slower. The partial condition `WHERE revoked = FALSE` limits the index to the exact set of rows the query needs. The `created_at DESC` ordering matches the natural display order (most recent first).

**Why not a composite index on `(user_id, device_id)`?** The primary session query patterns are "all sessions for user" and "all sessions for device" — never the intersection. A composite would be wasteful. Two separate indexes are preferable.

---

### 8.3 `refresh_tokens` Indexes

```sql
-- Refresh flow: primary lookup by token hash (THE hot path)
-- Covered by the UNIQUE constraint on token_hash. No additional index needed.

-- Revoke all tokens for a session (logout single session)
CREATE INDEX idx_refresh_tokens_session_id
    ON refresh_tokens (session_id);

-- Revoke all tokens for a user (password change, logout-all)
CREATE INDEX idx_refresh_tokens_user_id
    ON refresh_tokens (user_id);

-- Background cleanup: find expired and consumed tokens
CREATE INDEX idx_refresh_tokens_expires_consumed
    ON refresh_tokens (expires_at)
    WHERE consumed_at IS NOT NULL OR revoked = TRUE;
```

**Why is the `token_hash` lookup covered by the unique constraint?** PostgreSQL automatically creates a B-tree index to enforce a `UNIQUE` constraint. There is no need for a separate `CREATE INDEX` — adding one would create a duplicate index, wasting space and adding write overhead.

**Why `idx_refresh_tokens_user_id`?** This is the index that enables the fast "revoke all for user" write in the `AuthService.ChangePassword` and logout-all flows. Without it, those operations would require a full table scan or an expensive join through sessions. This is a write-path index, not a read-path index.

---

### 8.4 `devices` Indexes

```sql
-- Device recognition at login: find a user's device by fingerprint
CREATE UNIQUE INDEX uq_devices_user_fingerprint_active
    ON devices (user_id, fingerprint_hash)
    WHERE revoked = FALSE;

-- List active devices for user (device management UI)
CREATE INDEX idx_devices_user_id_active
    ON devices (user_id, last_active_at DESC)
    WHERE revoked = FALSE;

-- Count active devices for limit enforcement
-- Covered by idx_devices_user_id_active above (same index usable for COUNT).
```

**Why `uq_devices_user_fingerprint_active` is a partial unique index?** The invariant is "a user may not have two active (non-revoked) devices with the same fingerprint." Once a device is revoked, a new device can be registered with the same fingerprint (the fingerprint is re-used by the same physical device logging in again). A full unique index on `(user_id, fingerprint_hash)` would prevent this re-registration. The `WHERE revoked = FALSE` partial condition enforces the right invariant.

---

### 8.5 `roles` and `permissions` Indexes

```sql
-- Permission resolution: find roles for a user
CREATE INDEX idx_user_roles_user_id
    ON user_roles (user_id);

-- Permission resolution: find permissions for a role
CREATE INDEX idx_role_permissions_role_id
    ON role_permissions (role_id);
```

**Why are the primary keys not sufficient?** The composite PKs `(user_id, role_id)` and `(role_id, permission_id)` support point lookups well, but the permission resolution query pattern is `WHERE user_id = $1` (get all roles for a user) followed by `WHERE role_id = ANY($1)` (get all permissions for those roles). These are leading-column lookups on the composite PK, so they are covered. The explicit indexes above are added for clarity but may be redundant with the PK indexes in practice — the optimizer will choose the PK index.

---

### 8.6 `email_verification_tokens` and `password_reset_tokens` Indexes

```sql
-- Find active token for a user (to invalidate before issuing a new one)
CREATE INDEX idx_email_verification_user_id
    ON email_verification_tokens (user_id)
    WHERE used_at IS NULL;

CREATE INDEX idx_password_reset_user_id
    ON password_reset_tokens (user_id)
    WHERE used_at IS NULL;

-- Token validation lookups are covered by the UNIQUE constraint on token_hash.
```

**Why partial indexes on `WHERE used_at IS NULL`?** These indexes exist to support the "invalidate previous tokens before issuing a new one" operation. Once a token is consumed, it is never queried by `user_id` again (only by `token_hash`, which has its own unique index). The partial condition keeps these indexes small.

## 9. Constraint Design

Constraints are the second layer of data integrity after the schema types themselves. Every constraint here corresponds to a documented business rule or invariant.

### 9.1 Uniqueness Constraints

| Table | Constraint | Columns | Invariant |
|---|---|---|---|
| `users` | `uq_users_email` | `email` | BR-01: email globally unique |
| `users` | `uq_users_username` | `username` | BR-02: username globally unique |
| `users` | `uq_users_email_lower` (index) | `lower(email)` | BR-01: case-insensitive |
| `users` | `uq_users_username_lower` (index) | `lower(username)` | BR-02: case-insensitive |
| `roles` | `uq_roles_name` | `name` | Role names are immutable and globally unique |
| `permissions` | `uq_permissions_name` | `name` | Permission names are immutable and globally unique |
| `refresh_tokens` | `uq_refresh_tokens_token_hash` | `token_hash` | INV-04: each token hash is unique |
| `email_verification_tokens` | `uq_email_verification_token_hash` | `token_hash` | Each verification token hash is unique |
| `password_reset_tokens` | `uq_password_reset_token_hash` | `token_hash` | Each reset token hash is unique |
| `devices` | `uq_devices_user_fingerprint_active` (partial index) | `(user_id, fingerprint_hash)` WHERE `revoked = FALSE` | A user cannot have two active devices with the same fingerprint |

### 9.2 Referential Integrity (Foreign Keys)

All foreign keys are enumerated in §6 and §7. Key decisions:
- Cascade deletes propagate through the user → device → session → refresh_token chain when a user is permanently deleted.
- RESTRICT prevents accidental deletion of roles with active users, or permissions assigned to roles.
- SET NULL preserves audit trails (`replaced_by_id`, `assigned_by`) when referenced rows are purged.

### 9.3 Check Constraints

| Table | Constraint | Expression | Purpose |
|---|---|---|---|
| `users` | `ck_users_email_not_empty` | `email <> ''` | Prevents storing an empty email |
| `users` | `ck_users_username_not_empty` | `username <> ''` | Prevents storing an empty username |
| `users` | `ck_users_password_not_empty` | `password_hash <> ''` | Guards against a bug in the hash layer sending an empty string |

| `sessions` | `ck_sessions_expires_future` | `expires_at > created_at` | A session that expires before or at creation time is nonsensical |
| `sessions` | `ck_sessions_revoked_at` | `(revoked = FALSE AND revoked_at IS NULL) OR (revoked = TRUE AND revoked_at IS NOT NULL)` | The revocation timestamp must be consistent with the revocation flag |
| `refresh_tokens` | `ck_refresh_tokens_expires_future` | `expires_at > issued_at` | A token that expires before issuance is nonsensical |
| `refresh_tokens` | `ck_refresh_tokens_revoked_at` | Same pattern as sessions | Revocation flag/timestamp consistency |
| `refresh_tokens` | `ck_refresh_tokens_hash_not_empty` | `token_hash <> ''` | Guards against storing an empty hash |

## 10. Trigger Design

### `fn_set_updated_at` (shared trigger function)

A single trigger function is defined once and attached to any table that carries an `updated_at` column. This avoids duplicating the logic per table.

```sql
CREATE OR REPLACE FUNCTION fn_set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$;
```

### Per-table trigger attachment

```sql
-- users
CREATE TRIGGER trg_users_updated_at
    BEFORE UPDATE ON users
    FOR EACH ROW
    EXECUTE FUNCTION fn_set_updated_at();
```

**Why a trigger for `updated_at` rather than application-managed?**  
The application is the primary setter. However, any direct SQL operation (administrative scripts, migration side effects, manual fixes) would bypass application code and leave `updated_at` stale. The trigger is a safety net. It also eliminates an entire class of bugs where a developer forgets to set `updated_at` in a new repository method.

**Which tables have `updated_at`?** Only `users`. Sessions, tokens, and devices do not have a generic `updated_at` — their mutations are tracked through specific semantic columns (`last_active_at`, `consumed_at`, `revoked_at`). The `roles` and `permissions` tables are seeded once and rarely mutated; the absence of `updated_at` reflects that.

## 11. Soft Delete Policy

### Tables with soft delete

| Table | Mechanism | Why |
|---|---|---|
| `users` | `deleted_at TIMESTAMPTZ NULL` + `status = 'deleted'` | 30-day grace period. Email and username remain reserved during grace period. Personal data removal happens after grace period via background job. |

### Tables with revocation (logical equivalent of soft delete)

| Table | Mechanism | Why |
|---|---|---|
| `sessions` | `revoked BOOLEAN` + `revoked_at TIMESTAMPTZ NULL` | Sessions are revoked, not deleted. The record is retained for audit and device management history. |
| `devices` | `revoked BOOLEAN` + `revoked_at TIMESTAMPTZ NULL` | A revoked device fingerprint must not match new logins. Retaining the record allows re-registration detection. |
| `refresh_tokens` | `consumed_at` + `revoked` | Tokens are consumed or revoked, never deleted during the active rotation window. They are purged by a background job after the retention window. |

### Tables with hard delete only

| Table | Why |
|---|---|
| `email_verification_tokens` | After use, these tokens have no value. They are candidates for periodic purging. |
| `password_reset_tokens` | Same as above. |
| `roles` | System roles are never deleted. Custom roles (future) will be hard-deleted after unassigning users. |
| `permissions` | Permissions are never deleted. |
| `user_roles` | An unassigned role is simply removed from this table. There is nothing to soft-delete. |
| `role_permissions` | Same. |

### Grace period implementation

During the user grace period (30 days after `deleted_at` is set), the user's email and username remain reserved because the `users` row still exists. The background cleanup job queries:

```sql
SELECT id FROM users
WHERE deleted_at IS NOT NULL
  AND deleted_at < NOW() - INTERVAL '30 days'
  AND status = 'deleted';
```

For each result, it deletes child records in dependency order (tokens → refresh_tokens → sessions → devices → user_roles) before deleting the user row itself. The FK cascade settings would handle most of this automatically, but explicit ordering is safer and auditable.

## 12. Token Storage Strategy

### Refresh tokens

Plaintext refresh tokens are **never** stored in the database. The persistence model stores only the SHA-256 hex digest of the plaintext token.

```
Client holds:    "a3f7c2d1e8b4..."  (256-bit random, URL-safe base64)
DB stores:       SHA256("a3f7c2d1e8b4...") = "4e07408562b..."
Lookup path:     SELECT * FROM refresh_tokens WHERE token_hash = SHA256($plaintext)
```

This means:
- A database breach leaks only hashes — computationally infeasible to reverse (given sufficient entropy in the plaintext token, which is mandated at ≥256 bits).
- The unique constraint on `token_hash` is the database's guarantee of hash collision safety.
- The application layer is responsible for computing `SHA256(plaintext)` before every INSERT and SELECT.

### Email verification tokens and password reset tokens

Identical storage strategy: `token_hash = SHA256(plaintext)`.

### Access tokens (JWTs)

Access tokens are **not stored in the database at all**. They are stateless, self-validating credentials signed by the server. The database is not consulted on every authenticated request — only on refresh token rotation, session management operations, and WebSocket establishment.

### Token retention policy

| Token type | Retention after expiry/consumption |
|---|---|
| `refresh_tokens` | 7 days after `expires_at` (to support replay detection for recently consumed tokens) |
| `email_verification_tokens` | 24 hours after `expires_at` or `used_at` |
| `password_reset_tokens` | 24 hours after `expires_at` or `used_at` |

These are suggestions for the background cleanup job, not schema constraints.

## 13. Performance Considerations

### Query patterns and their optimizations

| Operation | Query pattern | Index used | Frequency |
|---|---|---|---|
| Token refresh | `SELECT * FROM refresh_tokens WHERE token_hash = $1` | `uq_refresh_tokens_token_hash` (unique) | High: every 15 min per active session |
| Session lookup | `SELECT * FROM sessions WHERE id = $1` | Primary key | Medium: WebSocket establishment |
| Login by email | `SELECT * FROM users WHERE lower(email) = lower($1)` | `uq_users_email_lower` | Medium: login events |
| Login by username | `SELECT * FROM users WHERE lower(username) = lower($1)` | `uq_users_username_lower` | Medium: login events |
| Device recognition | `SELECT * FROM devices WHERE user_id = $1 AND fingerprint_hash = $2 AND revoked = FALSE` | `uq_devices_user_fingerprint_active` | Medium: login events |
| Active session list | `SELECT * FROM sessions WHERE user_id = $1 AND revoked = FALSE ORDER BY created_at DESC` | `idx_sessions_user_id_active` | Low: device management UI |
| Active device list | `SELECT * FROM devices WHERE user_id = $1 AND revoked = FALSE ORDER BY last_active_at DESC` | `idx_devices_user_id_active` | Low: device management UI |
| Permission resolution | Join `user_roles → role_permissions → permissions WHERE user_id = $1` | `idx_user_roles_user_id` + `idx_role_permissions_role_id` | Very low: cache miss only |
| Revoke all sessions for user | `UPDATE sessions SET revoked = TRUE WHERE user_id = $1` | `idx_sessions_user_id_active` | Low: password change |
| Revoke all tokens for user | `UPDATE refresh_tokens SET revoked = TRUE WHERE user_id = $1` | `idx_refresh_tokens_user_id` | Low: password change |

### Write amplification on token refresh

Every token refresh is a 3-write transaction:
1. `UPDATE refresh_tokens SET consumed_at = $now, replaced_by_id = $new_id WHERE token_hash = $hash`
2. `INSERT INTO refresh_tokens (...)`
3. `UPDATE sessions SET last_active_at = $now WHERE id = $session_id`

These 3 writes hit 2 tables but touch 3 rows. The writes are sequential within a transaction. At scale, this is the dominant write pattern.

**Mitigation:** The refresh token table will grow with consumed tokens. The background purge job (running off-peak) removes consumed tokens older than the retention window to keep the table size bounded and index scans fast.

### Permission caching

The permission resolution join (§13 above) traverses `user_roles` → `role_permissions` → `permissions` — up to 3 table reads plus 2 joins per call. This is why `PermissionService` (§5.5 of the contracts) caches the result in Redis with a TTL. The database is hit only on a cache miss (typically after a role assignment change). At steady state, the database never sees permission resolution queries.

### Partitioning considerations

**`refresh_tokens` is the first candidate for range partitioning** by `issued_at` once the platform reaches scale. Partition by month, retaining only the current and previous month in the primary partition. Older partitions can be archived or dropped. The current schema is partitioning-compatible: `issued_at` is present and the primary key is a UUID (not a serial that would constrain partitioning).

**`sessions` is the second candidate**, partitioned by `created_at`. Active sessions are heavily read; historical revoked sessions are cold.

Neither partitioning nor archiving is implemented at this stage. The schema supports it without modification.

## 14. Future Extensibility

The schema is designed to accommodate the following future features without requiring breaking schema changes.

### 14.1 OAuth / Social Login

Add a new `oauth_identities` table:

```
oauth_identities
    id              UUID PK
    user_id         UUID NOT NULL FK → users.id (CASCADE)
    provider        TEXT NOT NULL  (e.g., 'google', 'github', 'discord')
    provider_user_id TEXT NOT NULL
    created_at      TIMESTAMPTZ NOT NULL
    UNIQUE (provider, provider_user_id)
```

The `users.password_hash` column would need to be made nullable to support users who signed up via OAuth with no password. This is a single-column alteration: `ALTER TABLE users ALTER COLUMN password_hash DROP NOT NULL`.

### 14.2 Multi-Factor Authentication (MFA)

Add an `mfa_factors` table:

```
mfa_factors
    id          UUID PK
    user_id     UUID NOT NULL FK → users.id (CASCADE)
    type        TEXT NOT NULL  (e.g., 'totp', 'sms', 'email_otp', 'backup_code')
    secret      TEXT NOT NULL  (encrypted TOTP secret or delivery address)
    verified    BOOLEAN NOT NULL DEFAULT FALSE
    created_at  TIMESTAMPTZ NOT NULL
    last_used_at TIMESTAMPTZ NULL
```

The `sessions` table gains a `mfa_verified BOOLEAN NOT NULL DEFAULT FALSE` column.

### 14.3 Passkeys (WebAuthn)

Add a `passkeys` table:

```
passkeys
    id              UUID PK
    user_id         UUID NOT NULL FK → users.id (CASCADE)
    device_id       UUID NULL FK → devices.id (SET NULL)
    credential_id   TEXT NOT NULL UNIQUE   (base64url-encoded credential ID)
    public_key      TEXT NOT NULL          (COSE-encoded public key)
    aaguid          TEXT NOT NULL DEFAULT ''
    sign_count      BIGINT NOT NULL DEFAULT 0
    created_at      TIMESTAMPTZ NOT NULL
    last_used_at    TIMESTAMPTZ NULL
```

### 14.4 Organizations (Multi-Tenancy)

Add an `organizations` table and an `organization_members` join table:

```
organizations
    id          UUID PK
    name        TEXT NOT NULL UNIQUE
    slug        TEXT NOT NULL UNIQUE
    created_at  TIMESTAMPTZ NOT NULL

organization_members
    organization_id UUID NOT NULL FK → organizations.id (CASCADE)
    user_id         UUID NOT NULL FK → users.id (CASCADE)
    role            TEXT NOT NULL  (org-scoped role: 'owner', 'admin', 'member')
    joined_at       TIMESTAMPTZ NOT NULL
    PRIMARY KEY (organization_id, user_id)
```

The `user_roles` table would gain an optional `organization_id UUID NULL` column to support organization-scoped role assignments.

### 14.5 Direct Permission Overrides

Add a `user_permission_overrides` table:

```
user_permission_overrides
    user_id       UUID NOT NULL FK → users.id (CASCADE)
    permission_id UUID NOT NULL FK → permissions.id (RESTRICT)
    granted       BOOLEAN NOT NULL  (TRUE = grant, FALSE = deny)
    assigned_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
    PRIMARY KEY (user_id, permission_id)
```

`PermissionService.GetUserPermissions` merges role-derived permissions with these overrides: denies take precedence over grants.

### Migration 000002 — `create_enum_types`

**What it does:** Defines the custom PostgreSQL enum types used across the schema.

```sql
-- up

    'active',
```

**Why separate from table creation?** Enum types must exist before the tables that reference them. Isolating them in their own migration makes the dependency explicit and allows adding new enum values in a future `ALTER TYPE ... ADD VALUE` migration without touching table DDL.

### Migration 000003 — `create_updated_at_trigger_function`

**What it does:** Creates the shared `fn_set_updated_at` function used by `updated_at` triggers.

```sql
-- up
CREATE OR REPLACE FUNCTION fn_set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$;

-- down
DROP FUNCTION IF EXISTS fn_set_updated_at;
```

**Why before tables?** The function must exist before the trigger can reference it. Triggers are attached in the same migration as their table.

### Migration 000017 — `seed_role_permissions`

**What it does:** Assigns permissions to system roles. This completes the initial RBAC setup. The assignment logic is expressed via CTEs to remain readable and immune to UUID generation order.

```sql
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id
FROM roles r, permissions p

    (r.name = 'user' AND p.name IN (
```

## Summary: Schema at a Glance

| Table | Rows (steady state) | Write frequency | Primary access pattern |
|---|---|---|---|
| `users` | Medium | Low (registration) | PK, email, username lookups |
| `devices` | Medium | Low (login from new device) | User + fingerprint lookup |
| `sessions` | High | Medium (per login) | PK, user + active filter |
| `refresh_tokens` | Very high (rotation chain) | High (every 15 min per session) | token_hash unique lookup |
| `roles` | Tiny (4 system) | Negligible | Full scan (cached) |
| `permissions` | Small (~10 initial) | Negligible | Full scan (cached) |
| `user_roles` | Medium | Low | user_id lookup |
| `role_permissions` | Small | Negligible | role_id lookup |
| `email_verification_tokens` | Low (ephemeral) | Low (registration) | token_hash lookup |
| `password_reset_tokens` | Very low (ephemeral) | Very low | token_hash lookup |
