## 1. Overview

The `friendships` table stores one immutable, canonical record for each established mutual friendship. It contains exactly two User endpoints and no directional, request, account-state, presentation, or preference data.

For users A and B, the persisted row always satisfies:

```
first_user_id < second_user_id
```

Consequently, `(A, B)` and `(B, A)` identify the same relationship. Friendship existence is represented by a row; removal physically deletes that row.

## 2. Conventions

The design follows the established authentication and Profile schema conventions.

| Element | Convention | Friends application |
|---|---|---|
| Table name | Plural `snake_case` | `friendships` |
| Primary key | `id UUID NOT NULL DEFAULT gen_random_uuid()` | `pk_friendships` |
| Foreign key column | Descriptive singular `snake_case` ending in `_id` | `first_user_id`, `second_user_id` |
| Timestamp | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | `created_at` |
| Constraint names | `pk_`, `fk_`, `ck_`, `uq_` prefixes | See sections 5-8 |
| Explicit indexes | `idx_{table}_{columns}` | See section 9 |

`pgcrypto`, which provides `gen_random_uuid()`, already exists from migration `000001_create_users`. No extension, enum, trigger, or UUID mechanism is introduced by Friends.

## 3. Table Definition

The following is the authoritative table blueprint for the future migration; it is not a migration file.

```sql
CREATE TABLE friendships (
    id              UUID        NOT NULL DEFAULT gen_random_uuid(),
    first_user_id   UUID        NOT NULL,
    second_user_id  UUID        NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_friendships
        PRIMARY KEY (id),

    CONSTRAINT fk_friendships_first_user_id
        FOREIGN KEY (first_user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_friendships_second_user_id
        FOREIGN KEY (second_user_id) REFERENCES users (id) ON DELETE CASCADE,

    CONSTRAINT ck_friendships_distinct_users
        CHECK (first_user_id <> second_user_id),
    CONSTRAINT ck_friendships_canonical_user_order
        CHECK (first_user_id < second_user_id),

    CONSTRAINT uq_friendships_user_pair
        UNIQUE (first_user_id, second_user_id)
);
```

## 4. Column Definitions

| Column | Type | Nullability | Default | Mutability | Purpose |
|---|---|---|---|---|---|
| `id` | `UUID` | `NOT NULL` | `gen_random_uuid()` | Immutable | Surrogate primary key, generated by PostgreSQL using the project-standard mechanism. |
| `first_user_id` | `UUID` | `NOT NULL` | None | Immutable | Lower UUID endpoint of the canonical unordered pair. References `users(id)`. |
| `second_user_id` | `UUID` | `NOT NULL` | None | Immutable | Higher UUID endpoint of the canonical unordered pair. References `users(id)`. |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL` | `NOW()` | Immutable | Database-generated timestamp for when the friendship became established. |

The schema stores User IDs, never Profile IDs. Presentation data remains owned by `profiles`, while account lifecycle remains owned by `users`.

## 5. Primary Key

`pk_friendships PRIMARY KEY (id)` provides the UUID surrogate identity used by the Friendship entity and follows the existing table convention. PostgreSQL automatically creates the associated B-tree index.

The database default `gen_random_uuid()` is the established generation mechanism. It remains compatible with application-assigned UUIDs where a future service constructs one before insertion, but no new generation mechanism is needed.

## 6. Foreign Keys and User Deletion

| Constraint | Reference | Delete behavior | Rationale |
|---|---|---|---|
| `fk_friendships_first_user_id` | `first_user_id → users(id)` | `ON DELETE CASCADE` | A Friendship cannot exist without its first endpoint. |
| `fk_friendships_second_user_id` | `second_user_id → users(id)` | `ON DELETE CASCADE` | A Friendship cannot exist without its second endpoint. |

When a User is hard-deleted after the established soft-delete grace period, PostgreSQL deletes every Friendship row containing that User in either endpoint column. This aligns with the Profile and authentication dependent-data policy.

Soft deletion does not delete Friendship rows. Neither user lifecycle state nor visibility is encoded in this table: soft-deleted and suspended users are handled by account and service policies.

## 7. CHECK Constraints

| Constraint | Expression | Guarantee |
|---|---|---|
| `ck_friendships_distinct_users` | `first_user_id <> second_user_id` | A user cannot be friends with themselves. |
| `ck_friendships_canonical_user_order` | `first_user_id < second_user_id` | Every row uses the one accepted ordering for an unordered pair. |

The canonical-order constraint also implies distinct endpoints, but both checks are retained intentionally. The distinct-user constraint documents and independently protects the direct domain rule, while canonical order protects representation consistency.

Application code must normalize inputs and reject self-friendship for clear domain errors. These database checks remain the final protection against direct writes and application defects.

## 8. Unique Constraint

`uq_friendships_user_pair UNIQUE (first_user_id, second_user_id)` ensures one row per canonical pair. It creates a B-tree index that directly supports canonical friendship-existence checks:

```text
WHERE first_user_id = :first_user_id
  AND second_user_id = :second_user_id
```

No separate pair lookup index, hash, or duplicate directional record is required. The unique index can also serve queries constrained by `first_user_id`, but it cannot efficiently satisfy the required ordering for paginated friend lists or lookup by `second_user_id`; those needs justify the explicit indexes in section 9.

## 9. Indexes

Two explicit composite B-tree indexes are required in addition to the indexes automatically created by the primary key and unique constraint.

| Index | Definition | Purpose |
|---|---|---|
| `idx_friendships_first_user_created_at_id` | `(first_user_id, created_at DESC, id DESC)` | Retrieves and paginates friendships where the requested user is the first canonical endpoint. Supports stable Friends ordering without a separate sort for that branch. |
| `idx_friendships_second_user_created_at_id` | `(second_user_id, created_at DESC, id DESC)` | Retrieves and paginates friendships where the requested user is the second canonical endpoint. Also supports foreign-key cascade lookups for that endpoint. |

### Constraint-Provided Indexes

| Index | Provided by | Purpose |
|---|---|---|
| B-tree on `id` | `pk_friendships` | Row identity and referential lookups targeting Friendship IDs. |
| B-tree on `(first_user_id, second_user_id)` | `uq_friendships_user_pair` | Canonical pair existence checks, duplicate prevention, and foreign-key cascade lookups for `first_user_id`. |

### Deliberately Excluded Indexes

| Index | Reason not created |
|---|---|
| Single-column `first_user_id` | Redundant: the unique pair index and first-endpoint pagination index both begin with `first_user_id`. |
| Single-column `second_user_id` | Redundant: the second-endpoint pagination index begins with `second_user_id`. |
| `(created_at, id)` | Does not filter by endpoint and does not serve a defined query path. |
| Profile, status, request, block, or visibility indexes | Those columns and concerns do not belong to Friends. |

The two endpoint-specific indexes are justified despite the initial table size because they support the defined `GetFriends` query shape, deterministic cursor ordering, and each referencing foreign key. No other index is required initially.

## 10. Supported Query Patterns

| Query pattern | Canonical form | Supporting index or constraint |
|---|---|---|
| Friendship existence | Canonicalize `(A, B)` then filter both endpoints. | `uq_friendships_user_pair` |
| Friend list, first endpoint | Filter `first_user_id = :user_id`; order `created_at DESC, id DESC`. | `idx_friendships_first_user_created_at_id` |
| Friend list, second endpoint | Filter `second_user_id = :user_id`; order `created_at DESC, id DESC`. | `idx_friendships_second_user_created_at_id` |
| Full friend list | Combine the two endpoint result sets, then apply the stable global order and cursor. | Both endpoint pagination indexes |
| Friend count | Count rows where either endpoint equals the user ID. | Both endpoint-leading indexes |
| User hard deletion | Delete dependent rows involving either endpoint. | Endpoint-leading indexes and `ON DELETE CASCADE` |

The eventual list implementation may use `WHERE first_user_id = :user_id OR second_user_id = :user_id`, or combine two endpoint branches. The schema supports both endpoints without a full table scan. For cursor pagination ordered by `created_at DESC, id DESC`, a two-branch query may be preferable to preserve endpoint-specific index ordering before merging; exact query construction belongs to the later repository step.

## 11. Concurrency and Integrity

Concurrent requests for the same relationship must canonicalize their input before insertion. Thus `Establish(A, B)` and `Establish(B, A)` both attempt the same canonical pair.

`uq_friendships_user_pair` is the final database guarantee: at most one insert succeeds. A future service may perform a prior existence check for a friendlier result, but it must translate a database duplicate-key error to `FRIENDS_ALREADY_FRIENDS` because pre-checks cannot prevent races.

The foreign keys and CHECK constraints protect the remaining structural invariants even if writes bypass the future application service.

## 12. Explicitly Excluded Fields

The initial `friendships` table contains only `id`, `first_user_id`, `second_user_id`, and `created_at`. It must not contain:

- Friend Request state or request identifiers
- Block, Privacy, Presence, moderation, or notification state
- User Preferences
- User or Profile attributes such as username, display name, email, avatar URL, or bio
- Friend counts or aggregate counters
- `status`, `updated_at`, `deleted_at`, soft-delete markers, tombstones, or history fields
- Directional relationship flags, follower/following fields, nicknames, notes, or other per-relationship metadata

## 13. Migration Considerations

The next available migration number is **`000015`**. The existing sequence ends at `000014_create_profiles`; `000011` remains intentionally unused and must not be backfilled or renumbered.

The eventual `000015_create_friendships` migration must:

1. Create `friendships` with the table definition and named constraints in this document.
2. Create the two explicit endpoint pagination indexes from section 9.
3. Depend on migration `000001_create_users` for `users`, `pgcrypto`, and `gen_random_uuid()`.
4. Require no `updated_at` trigger, enum, extension, user/profile alteration, counter trigger, or seed data.
5. Provide a corresponding rollback that drops only Friends-owned indexes and the `friendships` table, leaving shared authentication infrastructure intact.
